# Conduit — LAN VPN Proxy 桌面化可行性报告

> **项目代号**：Conduit（导管）
> 日期：2026-04-30
> 范围：把 `task/20260429-lan-vpn-proxy/` 下的 Python CLI 代理（HTTP+SOCKS5+PAC）封装成「双击即用」的桌面应用，并新增实时流量可视化

| 维度 | 解释 |
|---|---|

- 前端工程：`conduit-ui`

## 1. 背景与目标

### 1.1 现状

当前实现是一个 Python asyncio CLI 服务（`proxy_server.py` + `run.sh`），核心能力：

| 能力 | 端口 / 路径 | 说明 |
|---|---|---|
| HTTP / HTTPS 代理 | `0.0.0.0:8080` | 含 CONNECT 隧道、绝对 URI 转发 |
| SOCKS5 代理 | `0.0.0.0:1080` | RFC 1928，CMD=CONNECT、NO-AUTH |
| PAC 自动配置 | `http://A:8080/proxy.pac` | 同端口提供，支持 `__PROXY_HOST__` 占位符替换 |
| 状态查询 | `GET /status` | 返回 CIDR 白名单、PAC 规则统计（JSON） |
| 路由检查 | `GET /check?host=X` | 解释一个目标会走 DIRECT 还是 PROXY |
| 启动横幅 | 终端打印 | 列出全部网卡、VPN 路由、HTTP/SOCKS/PAC URL、CIDR 白名单 |
| LAN 白名单 | 默认 RFC1918 | 192.168.x / 10.x / 172.16-31.x，启动时强制风险二次确认 |

启动方式目前仍依赖终端：`./run.sh start -d` → `./run.sh status` → `./run.sh stop`。

### 1.2 GUI 化目标（用户原始需求）

1. **双击启动**：终端用户、非工程师也能用，不需要 `cd` + 命令行
2. **显示有哪些机器连接了**：实时活跃客户端列表（来源 IP / 协议 / 当前流量）
3. **每台机器实时流量折线图**：每个客户端独立曲线，区分上行 / 下行，时间窗 30s ~ 5min 可切换
4. **显示当前 IP**：本机所有 IPv4 网卡（区分物理网卡 / VPN tun / loopback），高亮"应分享给 LAN 的那一个"
5. **告知 B 如何连接**：把 PAC URL / HTTP / SOCKS 配置一键复制 + 二维码 + 配套图文步骤
6. **可选**：托盘常驻、日志窗口、配置面板、自动检测 VPN 是否在线

### 1.3 GUI 化的价值

- **降低使用门槛**：从"会 shell 的工程师"扩到"任何 LAN 用户"
- **降低误操作风险**：UI 里强制二次确认 + 实时显示风险（VPN 未连、绑了非 LAN 网卡等）
- **降低排错成本**：B 端连不上时，A 端 GUI 能直接看到"B 的 IP 是不是在白名单内"、"刚才有没有握手日志"

## 2. 现有代码与 GUI 之间的差距

把 CLI 包装成 GUI，**不是简单加个外壳**，需要补三块能力：

| 缺什么 | 现状 | 需要新增 |
|---|---|---|
| **活跃连接表** | 仅在日志里能看到（INFO 级） | 进程内维护 `dict[client_ip, ConnectionInfo]`，含首次连接时间、最近活跃、协议、目标 host:port、累计字节数 |
| **流量采样环 / 折线图数据源** | 仅 close 时有总字节数 | `relay.py` 中每次 `chunk` 之后增量累加，按 1 秒粒度采样到 `RingBuffer(per_ip, 600s)`；前端拉折线就是切片这块环 |
| **状态推送通道** | `/status` 只返回静态配置 | 新增 `/events` (SSE) 或 `/ws` (WebSocket)，前端订阅；或简化为 `/status` 加上 `active_clients` 字段 + 前端 1s 轮询 |
| **生命周期控制** | 只能 `kill SIGTERM` | 提供 `/admin/stop`（仅 127.0.0.1）；GUI 进程负责 spawn/kill 子进程 |
| **IP 自检 / 引导信息** | 启动横幅一次性打印 | 接口化：`/info` 返回所有网卡 + 当前 LAN IP + 默认路由 + 是否 VPN，前端实时展示 |

> 这部分改造无论选哪个技术栈都要做，**改动集中在 `http_proxy.py` + `proxy_server.py`**，约 200 行。

## 3. 候选技术栈对比

下面 5 套方案，按"复用现有 Python 后端的程度"从高到低排序。

### 方案 A：PyWebview + Vue 3（保留 Python 后端）

```
┌────────────────────────────────┐
│  app.py  (Python 主进程)       │
│  ├─ pywebview 创建 Webview 窗口 │
│  └─ asyncio 跑 proxy_server     │  ← 复用现有代码
│        (8080/1080 监听 LAN)     │
│  Webview 加载 dist/index.html  │
│   (Vue 3 + Vite 打包)          │
└────────────────────────────────┘
        前后端共进程，pywebview.api 暴露 Python 函数给 JS
```

| 维度 | 评估 |
|---|---|
| 复用现有代码 | ⭐⭐⭐⭐⭐ 几乎 100% 复用，只需把 `proxy_server.main()` 改成 async task |
| 包体积 | macOS ~30MB（依赖系统 WebKit），Windows ~25MB（依赖 Edge WebView2，需要预装运行时） |
| 性能 | ⭐⭐⭐⭐ Python asyncio + 系统 Webview，启动 1-2s |
| 开发速度 | **最快**：保留 Python 全部代码，前端独立 Vue3 项目，2-3 天能出 MVP |
| 跨平台 | macOS / Windows / Linux 全支持 |
| 双击启动 | macOS 用 `py2app`，Windows 用 `pyinstaller --noconsole`，Linux 用 AppImage |
| 维护 | ⭐⭐⭐⭐ 单一语言（Python+Vue），团队上手成本最低 |
| 弱点 | Windows 需要 Edge WebView2 运行时（Win10 1809+ 一般已预装）；打包后 Python 解释器 + 依赖会膨胀到 50-80MB |

## 4. 推荐方案

### 4.1 短期（"出活优先"）→ **方案 A：PyWebview + Vue 3**

理由：
- Python 代码 100% 复用，**最低风险**
- 2-3 天能出可用版本
- 包大点（~60MB）但能接受，毕竟是内部工具
- 一旦验证产品可行，再升级到方案 B 不痛

### 4.2 长期（"产品化"）→ **方案 B：Tauri 2 + Vue 3 + Python sidecar**

理由：
- 包体积小（~40MB），启动快
- Tauri 生态完善：自动更新、签名、托盘都开箱即用
- 后端依旧是 Python，演进自由（未来可逐步把热点路径迁到 Rust）
- 工程感更强，给非工程师用户的"专业感"远好于 PyWebview

### 4.3 何时考虑方案 D / E

- 如果未来这个工具要走出"内部小工具"的范围（例如对外发布、ARM 嵌入式、长时间高并发），把后端用 Rust/Go 重写一次再合理不过。
- 现阶段**不推荐**作为起步方案，投入产出比太低。

## 5. 关键技术点（无论选哪套都得做）

### 5.1 后端改造（Python 侧，方案 A/B/C 通用）

```
新增 active_connections.py
   ├─ class ConnectionRegistry  # 进程级单例（asyncio.Lock 保护）
   │    add(peer_ip, proto, target_host, target_port) -> session_id
   │    update_bytes(session_id, delta_sent, delta_recv)  # 每 chunk 调一次
   │    remove(session_id)
   │    snapshot() -> list[dict]   # 给 /status / /events 用
   │
   ├─ class TrafficSampler        # 折线图数据源
   │    每 1s 把每个 peer_ip 的 (sent_total, recv_total) 增量
   │    push 到一个 deque(maxlen=600)（10 分钟环）
   │    series(peer_ip, window_sec) -> [(t, sent_bps, recv_bps), ...]
   │
   └─ 在 http_proxy._handle_connect / _handle_absolute /
         socks5_proxy.handle_socks5 / relay.bidirectional_relay 里加埋点
         relay 的循环里每次 read 后就 update_bytes

修改 http_proxy._serve_status
   返回 active_clients = registry.snapshot()
   字段：peer_ip, proto, target, since, last_seen,
         sent_bytes, recv_bytes, sent_bps_1s, recv_bps_1s

新增 /traffic?peer=192.168.1.158&window=60
   返回 [(t, sent_bps, recv_bps), ...] 折线图直接吃

新增 /events (SSE)
   每秒 push 一次：
   {
     "active_clients": [...],          # 表格 + 折线最新点
     "traffic_tick": {"192.168.1.158": [t, sent_bps, recv_bps], ...},
     "route_iface": "utun4",
     "lan_ip": "192.168.1.10",
     "vpn_ok": true
   }
   前端用 EventSource 订阅，前端图表只 push 新点（不重绘历史）
```

> 这部分约 200 行 Python，是 Conduit GUI 化的**真正核心改动**。
> 折线图最贵的部分是 `relay.py` 里加字节计数——一定要保证 hot path 上**没有锁竞争**（用单线程 asyncio + 原子 dict 写就够，不要用 `threading.Lock`）。

### 5.2 前端组件设计（Vue 3 + Vite + Tailwind 推荐）

```
conduit-ui/src/
├─ App.vue                # 顶层布局
├─ components/
│   ├─ ProxyControl.vue   # 启动/停止按钮、端口配置
│   ├─ NetworkPanel.vue   # 当前网卡列表、VPN 状态、当前 LAN IP（醒目）
│   ├─ ClientList.vue     # 实时连接表（peer_ip / proto / 当前速率 / 累计流量）
│   ├─ TrafficChart.vue   # 各机器实时流量折线图（每 IP 一条曲线，可叠加上下行）
│   ├─ ShareCard.vue      # B 端连接引导（PAC URL / SOCKS / 二维码 / 一键复制）
│   └─ LogViewer.vue      # 滚动日志窗口（tail -f）
└─ composables/
    ├─ useEvents.ts       # EventSource 封装
    └─ useTraffic.ts      # 折线图数据流（订阅 traffic_tick，按 IP 维护 deque）
```

`TrafficChart.vue` 关键点：
- **图表库选型**：
  - `uPlot` ⭐ 推荐——专为时序流式数据优化，1 秒 1 点完全无压力，包仅 ~40KB
  - `Chart.js` 备选——生态成熟，但流式更新需要手动调 `update('none')`
  - `ECharts` 不推荐——包大（~1MB），杀鸡用牛刀
- **交互**：
  - 顶部 toggle：30s / 1min / 5min / 10min 时间窗
  - 图例可点击隐藏某 IP
  - hover 显示 tooltip：`192.168.1.158  ↑ 12.3 KB/s  ↓ 540 KB/s`
  - 上下行用两条不同色或同色虚实线表达
- **数据源**：
  - 首次加载：`GET /traffic?window=60` 拿历史 60s 各 IP 序列
  - 之后：订阅 `/events`，每秒一个 tick 增量 push 到曲线尾部
  - 旧点 shift 出 deque（保持最多 600 点）

`ShareCard.vue` 关键点：
- 三个 Tab：**PAC（推荐）/ HTTP / SOCKS5**
- 每个 Tab 给出：URL、对应的 macOS / Windows / iOS 配置截图与文字步骤
- URL 旁带「复制」按钮 + 二维码（用 `qrcode` npm 包），手机用户扫码就能看到说明页

### 5.3 双击启动 / 打包

| 平台 | 方案 A 打包 | 方案 B 打包 |
|---|---|---|
| macOS | `py2app` → `.app` | `tauri build` + sidecar bundle，需 codesign + notarytool |
| Windows | `pyinstaller --noconsole --onefile` → `.exe` + 安装器 | `tauri build` → `.msi` 或 `.exe`（NSIS）|
| Linux | `pyinstaller` + `.desktop` 文件 | `tauri build` → `.deb` / `.AppImage` |

macOS 需要解决：
- **Gatekeeper**：未签名 `.app` 双击会被拦，开发期建议右键 → 打开
- **本地网络权限弹窗**：首次绑定 `0.0.0.0:8080` 系统会弹"允许接收传入连接"，**必须允许**
- **沙盒**：不要开 sandbox，否则绑端口受限

### 5.4 端口冲突 / 防火墙提示

启动前端先调一次 `/healthcheck`：
- 8080/1080 被占用 → 提示用户改端口或停掉占用进程
- 默认路由不是 utun/ppp/tun → 黄色警告"VPN 似乎未连接"
- 找不到物理网卡 IP → 红色警告"无法分享给 LAN"

| 阶段 | 内容 | 预计工时（按方案 A） |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 公司 IT 政策禁止 VPN 共享 | UI 里强制保留 banner 风险提示；默认只 listen `192.168.0.0/16`；增加"仅在家庭 WiFi 启用"的勾选项 |
| macOS 防火墙拦截传入连接 | 首次启动检测，弹窗引导用户在「系统设置 → 网络 → 防火墙 → 选项」里允许本应用 |
| Python sidecar 在 macOS 公证里被拦 | 方案 B 选择 `pyoxidizer` 把 Python 嵌入单二进制；或者方案 A 直接 `py2app` 一并签名 |
| Windows Defender 误报代理类二进制 | 提交 Microsoft 误报申诉；或者用 EV 证书签名 |
| 端口被其他进程占用 | UI 里端口冲突自动检测 + 提供"自动选择空闲端口"按钮 |
| GUI 进程崩溃但 Python 还在跑 | GUI 启动时先 `kill old pid`，关闭时确保 Python 子进程被 kill（注册 `atexit` + `signal` handler）|
