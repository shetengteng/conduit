> 文档版本：v1.0  
> 创建日期：2026-05-06  
> 分支：`feat/python-to-rust-feasibility`  
> 状态：**Draft，待 review**

## 0. 摘要（结论先行）

**当前架构由三栈拼成**：Python（业务大脑）+ Rust/Tauri（桌面外壳）+ TypeScript/Vue（UI）。问题不在某一种语言"不好"，而在 **Python 与 Rust 之间多了一层 sidecar 进程边界**——改一个字段要动 Python / Rust / TS 三处，PyInstaller 打包带来 30~40MB/端 的体积、跨架构不能交叉编译、冷启动需要 healthz 轮询。

**推荐方案 A：Python → Rust，业务逻辑收进 Tauri 主进程**。理由：

1. PAC 引擎是项目自定义窄语法（regex + 三个固定 helper），**不需要嵌 JS 引擎**——这条曾是 A 方案最大风险，现已排除。
2. 其他 Python 模块（HTTP/SOCKS5/relay/mDNS/networksetup/route cache）都有成熟 Rust crate 平替，**无功能性 blocker**。
3. 真正"精简"= 减进程边界 + 减打包工具链。方案 A 一次到位，方案 B 只是换 sidecar 语言。
4. 长期收益：**1 个进程 / 1 套构建链 / 体积砍半 / 启动 < 0.3s / 类型安全**。

**预估工作量**：4~6 周全职（不含返工）。建议**分 4 阶段渐进切换**，每阶段都能跑通端到端，不破现网。

**短期"Plan B"**（如果不能立刻投入 4~6 周）：保留 Python+Rust 不动，先把 server-app/core 与 client-app/core 之间重复的代码（`events_bus.py` / `api/server.py` / mDNS 字段约定 / `relay.py`）合并成共享 package，至少减少**50% 的 Python 维护面**。这条不换语言，但当下就能落地。

## 1. 现状盘点

### 1.1 仓库结构

```
conduit/
├── server-app/
│   ├── core/        ← Python 7000 LOC（不含 tests）
│   ├── src-tauri/   ← Rust 800 LOC
│   └── ui/          ← Vue 3 + TS（共享 stack）
├── client-app/
│   ├── core/        ← Python 4800 LOC（更复杂，多 route_cache / connectivity）
│   ├── src-tauri/   ← Rust 800 LOC（多 autostart）
│   └── ui/          ← Vue 3 + TS
├── scripts/         ← Bash（build-sidecars.sh 等）
└── design/          ← 历史设计文档
```

### 1.2 各栈职责与代码量

| 栈 | 业务代码 LOC | tests LOC | 关键模块 | 依赖 |
|---|---|---|---|---|
| **Python** | ~7000（双端去重后约 5000） | ~4500 | `proxy_core.py` / `http_proxy.py` / `socks5_proxy.py` / `pac_engine.py` / `mdns_advertiser.py` / `discoverer.py` / `route_cache.py` / `route_resolver.py` / `system_proxy.py` / `connectivity.py` / `api/server.py` | `aiohttp` + `zeroconf`（仅这 2 个第三方） |
| **Rust (Tauri)** | ~1500 | 0 | `sidecar.rs`（spawn Python+watchdog） / `commands.rs`（IPC） / `tray.rs` / `healthz.rs` / `autostart.rs`（client 才有） | `tauri 2` / `tokio` / `reqwest` / `serde` / `portpicker` |
| **TS / Vue** | ~12000 | 部分 | UI 组件、views、i18n | Vue 3 + Vite 5 + shadcn-vue + Tailwind 4 + reka-ui |
| **Bash** | < 500 | — | `build-sidecars.sh` / `release.sh` / `bump-version.sh` / `e2e.sh` | — |

### 1.3 进程模型（关键）

```
┌──────────────────────────────────────────┐
│ Tauri Rust 主进程（窗口 / 托盘 / IPC）    │
│   spawn ↓                                │
│ ┌────────────────────────────────────┐   │
│ │ PyInstaller onedir Python sidecar  │   │
│ │  - HTTP proxy (8080)               │   │
│ │  - SOCKS5 (1080)                   │   │
│ │  - 控制 API (127.0.0.1:8090)       │   │  ← Rust 通过 reqwest 调它
│ │  - mDNS 广播                        │   │
│ └────────────────────────────────────┘   │
└──────────────────────────────────────────┘
```

- 启动时 Tauri 跑 `binaries-dir/conduit-server-sidecar/conduit-server-sidecar`，传 `--http-port`、`--socks-port`、`--api-port`、`--watchdog-ppid` 等参数。
- 跨进程通信走 **HTTP**（127.0.0.1:8090 上的 SSE / REST），不是 Tauri 原生 IPC。
- dev 模式 fallback 到 `python3 server-app/core/proxy_server.py`。

### 1.4 PAC 引擎真相（关键技术结论）

`server-app/core/pac_engine.py` **不是真 JS 解析器**，而是一个**正则提取器**：

- 把 `proxy.pac` 按 `// ---------- N. xxx ----------` 注释切成 5 段
- 每段用三条正则提取 `shExpMatch(host, "...")`、`dnsDomainIs(host, "...")`、`isInNet(host, "ip", "mask")`
- 解析结果是结构化的 `PacRules`（globs / domains / nets 列表）
- 浏览器拿到的 `proxy.pac` 仍是真 PAC 文件，由浏览器自己跑 JS

**含义**：Rust 改写时**不需要嵌 boa / quickjs / v8**。直接用 `regex` + `globset` + `ipnet` 三个 crate 即可平移，<300 行 Rust 代码。

## 2. 痛点分析（为什么要精简）

| 痛点 | 触发场景 | 影响 |
|---|---|---|
| **三栈维护** | 改一个字段（如 mDNS TXT 多加 `vpn_iface`） | 改 `mdns_advertiser.py` + `discoverer.py` + `commands.rs` + `client.ts` 共 4 处 |
| **PyInstaller 体积** | 每个 dmg 都要塞一个 onedir | 单端 30~40MB，双端总 dmg ~70MB |
| **跨架构不能交叉编译** | macOS arm64 + x86_64 + Win + Linux | 必须每个目标平台跑一次 `build-sidecars.sh` |
| **冷启动延迟** | Tauri spawn → sidecar 启动 → healthz 轮询 | 1~3 秒，需要 polling 才能确认就绪 |
| **进程边界** | watchdog ppid + kill_on_drop + healthz | 任何一个 hang 都要专门排错 |
| **本地开发依赖** | venv + cargo + pnpm 三个生态 | onboard 新人成本高 |
| **签名 / 公证** | macOS notarization 要单独处理 sidecar 二进制 | release 流程比纯 Tauri 多步 |
| **依赖审计** | aiohttp + zeroconf + 23 个 transitive | Python 端 `~/.conduit` 缓存额外目录 |

**共同根因**：选用 Python 是因为初期 socket-heavy 业务用 `asyncio` 写得快，但落到桌面应用打包时，Python 不是 first-class citizen。Tauri 生态的"原生选择"是 Rust。

## 3. 方案 A：Python → Rust（合并进 Tauri 主进程）

### 3.1 目标架构

```
┌────────────────────────────────────┐
│ Tauri Rust 主进程                   │
│  - tauri::App（窗口 / 托盘 / IPC） │
│  - tokio runtime                   │
│  - HTTP proxy listener (8080)      │
│  - SOCKS5 listener (1080)          │
│  - mDNS 广播 / 浏览器               │
│  - PAC engine（regex 平移）         │
│  - networksetup subprocess         │
│  - 状态通过 tauri::Emit 推 UI      │
└────────────────────────────────────┘
                                       
没有 sidecar / 没有 127.0.0.1 控制 API / 没有 PyInstaller
```

### 3.2 模块改写映射

| 原 Python 模块 | LOC | 改写后 Rust crate / 模块 | 新 LOC 估算 | 难度 |
|---|---|---|---|---|
| `pac_engine.py` | 192 | `regex` + `globset` + `ipnet` | ~300 | ⭐ 低 |
| `proxy.pac`（资源文件） | — | embed via `include_str!` | — | — |
| `mdns_advertiser.py` | 154 | `mdns-sd` crate | ~250 | ⭐⭐ 中 |
| `discoverer.py`（client） | 477 | `mdns-sd` 浏览模式 | ~600 | ⭐⭐ 中 |
| `http_proxy.py` | 454 | `hyper` + 自写 CONNECT | ~700 | ⭐⭐⭐ 高 |
| `socks5_proxy.py` | 173 | tokio 直接写（参考 fast-socks5 crate） | ~300 | ⭐⭐ 中 |
| `relay.py` + `outbound.py` | ~330 | `tokio::io::copy_bidirectional` | ~200 | ⭐ 低 |
| `proxy_core.py` | 236 | `Arc<ProxyState>` + tokio::spawn | ~400 | ⭐⭐ 中 |
| `active_connections.py` | 333 | `DashMap<ConnId, ConnInfo>` + broadcast channel | ~400 | ⭐⭐ 中 |
| `traffic_meter.py`（client） | 117 | `AtomicU64` + interval ticker | ~150 | ⭐ 低 |
| `healthcheck.py` + `connectivity.py` | 434 | `reqwest` + `socket2` ping | ~500 | ⭐⭐ 中 |
| `system_proxy.py` | 273 | `std::process::Command` + 解析 | ~350 | ⭐ 低 |
| `route_cache.py` + `route_resolver.py` | 525 | `serde_json` 持久化 + `lru` | ~600 | ⭐⭐ 中 |
| `local_proxy.py` + `client_main.py`（client） | 1092 | tokio + axum | ~1200 | ⭐⭐⭐ 高 |
| `api/server.py` + 各 endpoint（双端） | ~600 | **去掉 HTTP API**，全部走 tauri::Emit + tauri::command | ~400 | ⭐⭐ 中 |
| `events_bus.py` | ~100 | `tokio::sync::broadcast` | ~80 | ⭐ 低 |
| `config.py` | 151 | `clap` + `serde` | ~150 | ⭐ 低 |
| **合计** | ~7000 | | **~7000** | — |

**关键发现**：Rust 代码量与 Python 大致 1:1，并不会膨胀（因为没了 dataclass 套娃和大量 docstring，由 type / lifetime 替代）。

### 3.3 依赖清单（新增 Rust crate）

```toml
# 在 server-app/src-tauri/Cargo.toml 与 client-app/src-tauri/Cargo.toml 中追加：
hyper = { version = "1", features = ["full"] }
hyper-util = { version = "0.1", features = ["tokio"] }
http-body-util = "0.1"
mdns-sd = "0.11"
regex = "1"
globset = "0.4"
ipnet = "2"
dashmap = "6"
lru = "0.12"
clap = { version = "4", features = ["derive"] }
chrono = "0.4"
nix = { version = "0.29", features = ["signal", "process"] }   # macOS networksetup 辅助
socket2 = "0.5"
```

**依赖体量**：约 80 个 transitive crate，编译后 release 二进制（Tauri + 全部上述）整体 ~25MB（vs 当前 Tauri 5MB + PyInstaller 30MB = 35MB），**净减 10MB**。

### 3.4 Tauri IPC 替代 HTTP 控制 API

**当前**：UI 通过 `fetch('http://127.0.0.1:8090/api/status')` 调 Python sidecar。  
**改写后**：UI 通过 `@tauri-apps/api/core` 的 `invoke('get_status')`，主进程 `#[tauri::command] fn get_status() -> Status`。

事件流（SSE）：
- 当前：Python 端 `/events` SSE → 浏览器 `EventSource`
- 改写后：Rust 端 `app.emit("connection-update", payload)` → UI 端 `listen('connection-update', cb)`

**收益**：
- 去掉 1 个端口（8090）
- 去掉 CORS / 鉴权代码
- 类型从 TS 一直推回 Rust（用 `serde_json::to_value` 或 `specta`）

### 3.5 不动的部分

| 模块 | 原因 |
|---|---|
| **UI（server-ui + client-ui）** | TS/Vue 已经是统一 stack，无需触碰，只改 IPC 调用方式（`fetch` → `invoke`） |
| **proxy.pac 文件** | 仍然作为静态资源，浏览器跑 |
| **release.sh / GitHub Actions** | 流程不变，只去掉 `build-sidecars.sh` 这一步 |
| **design/ 历史文档** | 保留作为历史参考 |

### 3.6 优势 / 劣势汇总

**优势**：
- ✅ **真正精简**：3 栈降到 2 栈（Rust + TS）
- ✅ **体积**：双端 dmg 总和从 ~70MB 降到 ~30MB
- ✅ **冷启动**：< 0.3s（vs 当前 1~3s）
- ✅ **类型安全**：编译期捕获跨层契约不一致
- ✅ **无 GIL**：tokio + epoll/kqueue 是 socket-heavy 应用最佳选择
- ✅ **跨架构交叉编译**：`cargo build --target aarch64-apple-darwin` 一行命令
- ✅ **签名简化**：只签一个 .app bundle，没有内部嵌套 sidecar 二进制

**劣势 / 成本**：
- ❌ 4~6 周全职工作（详见 §6 分阶段计划）
- ❌ 4500 行 Python tests 需要部分迁移（约 60% 即 2700 行）
- ❌ 团队 Rust 学习成本（如果你自己写则不算）
- ❌ mDNS 的 `mdns-sd` crate 在 macOS 与 zeroconf 互操作上**需要做 POC**（见 §5）
- ❌ 中间态：渐进迁移期间 server / client 可能临时存在"半 Python 半 Rust"，需要 feature flag 切流

## 4. 方案 B：Python → Node.js / TypeScript（替换 sidecar）

### 4.1 目标架构

保留 Tauri Rust 外壳，把 Python sidecar 换成 Node sidecar：

```
┌─────────────────────────────────────┐
│ Tauri Rust 主进程（窗口 / 托盘）    │
│   spawn ↓                           │
│ ┌─────────────────────────────────┐ │
│ │ Node.js sidecar (pkg / sea)     │ │
│ │  - HTTP proxy (8080)            │ │
│ │  - SOCKS5 (1080)                │ │
│ │  - 控制 API (127.0.0.1:8090)    │ │
│ │  - mDNS                          │ │
│ └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

### 4.2 收益与代价

| 维度 | 评估 |
|---|---|
| **统一 stack** | UI + sidecar 都用 TS，开发心智一致 |
| **PAC** | Node 自带 V8 vm，可以直接跑真 PAC（其实当前也不需要） |
| **mDNS** | `bonjour-service` / `mdns` npm 包，**质量参差**，issue 长期不修 |
| **HTTP/SOCKS5** | `socks` / `http-proxy` 现成 npm，但 SOCKS5 implementation 多年未维护 |
| **打包** | `pkg`（已停维护） / Node.js `--experimental-sea-config`（仍是 experimental） / `bun build --compile` |
| **体积** | Node binary 30~80MB（与 PyInstaller 同级，**没省**） |
| **进程边界** | **仍然需要 sidecar**（Tauri 不能内嵌 V8） |
| **性能** | socket-heavy 场景下 Node 比 tokio 慢 2~3 倍，但对 LAN 代理够用 |
| **启动** | Node 冷启动 ~200ms，比 PyInstaller 略快 |

### 4.3 评分：**不推荐**

方案 B 的本质是"换 sidecar 语言但不去 sidecar"。如果你的目标是"精简"，B 没有解决核心问题（进程边界 + 打包工具链）。除非你**特别在意团队全栈 TS**，否则 A 优于 B。

## 9. 替代方案：短期"先合并不换栈"

如果 4~6 周不能立即投入，**最小工作量的精简**：

### 9.1 Python core 双端共享化（约 1 周工作量）

当前 `server-app/core` 与 `client-app/core` 有大量近似代码：
- `events_bus.py`（双端字面相同）
- `relay.py`（双端基本相同）
- `api/server.py` + `api/errors.py` + `api/healthz.py`（双端 90% 相同）
- mDNS 字段约定（`_conduit._tcp.local.` + TXT）
- pyproject.toml 几乎相同

提议：
```
core-shared/                          ← 新增
├── pyproject.toml                    ← name = "conduit-core-shared"
└── src/conduit_core/
    ├── events_bus.py
    ├── relay.py
    ├── api/{server,errors,healthz}.py
    └── mdns_contract.py              ← 字段约定常量

server-app/core/  → depend on conduit-core-shared
client-app/core/  → depend on conduit-core-shared
```

**收益**：
- 维护面减 ~30%（约 2000 行重复代码）
- 不动 Rust / TS / 打包流程
- 可以作为方案 A 的"前置重构"——共享部分先聚拢，未来一次性 Rust 化更顺

**代价**：1 周工作量；PyInstaller spec 需要更新 hidden imports。

---

## 10. 决策建议

| 你的优先级 | 推荐路径 |
|---|---|
| **想长期一劳永逸 + 接受 4~6 周投入** | 方案 A，按 §6 分阶段执行，先做 §7 POC |
| **接下来 1 个月不能停业务、想快速止血** | 方案 §9（共享化），3 个月后再启动方案 A |
| **团队全 TS、不想引入 Rust 业务代码** | 方案 B（不推荐，但可行） |
| **觉得现状能用、不想改** | 不动，但要接受现有的 3 栈维护成本 |

**我的最终建议**：先做 **§7 的 5 个 POC（合计 3 天）**，POC 通过后再决定是直接进方案 A 的 Phase 1，还是先用 §9 的方案争取时间。POC 是低成本探针，不通过也是有价值的信息。
