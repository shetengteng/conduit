## 2. 一步步验收清单

### 2.1 启动准备

确认终端在项目根目录,Node 18+,Python 3.10+,macOS。检查 dev 模式 sidecar 行为:

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `CONDUIT_NO_MDNS=1` | 未设置 | server 启动时跳过 mDNS 广播(只用于隔离调试) |
| `CONDUIT_NO_SYSTEM_PROXY=1` | 未设置 | client 连接成功后不切系统代理(只用于隔离调试) |

不设置任何变量 = 推荐的"完整体验"模式。

### 2.2 启动两个 sidecar(2 个终端)

**终端 1:server-app**
```bash
cd /Users/TerrellShe/Documents/personal/tt-projects/conduit
pnpm dev:server
```
会拉起 Tauri 主窗口 + Python sidecar。等到看到 `mDNS advertised: Conduit on ...` 表示 server 就绪。

**终端 2:client-app**
```bash
cd /Users/TerrellShe/Documents/personal/tt-projects/conduit
pnpm dev:client
```
拉起 client Tauri 窗口。第一次 macOS 会弹出 **本地网络访问权限**,**必须点允许**(否则 mDNS 收不到广播)。

### 2.3 「发现」页验收

1. 应在 5–10 秒内看到 server 卡片(name 为本机主机名)
2. 卡片右上"在线"绿点
3. 卡片显示 host:port、SOCKS / API 端口、VPN ✓、版本号、广播时间
4. 点「重新扫描」按钮无报错
5. 关掉 server-app(终端 1 Ctrl+C)→ 大约 1–2 分钟后卡片变灰显示「曾见过 X 分钟前」

> **如果发现页空着**:
> - 卡片永远不出来 → macOS 系统设置 → 隐私与安全性 → 本地网络 → 允许 client-app
> - 显示"自动发现未启用" → sidecar 未装 zeroconf,执行 `pip install zeroconf` 后重启 client

### 2.4 「连接」流程验收

1. 重启 server(终端 1 重新跑 `pnpm dev:server`),client 「发现」页 server 卡片重新变绿
2. 点卡片上的「连接」按钮
3. 自动跳转到「已连接」标签页
4. 看到 5 步竖向 stepper:
   - ① 可达性检查 → 绿勾,detail "延迟 N ms"
   - ② 拉取 PAC → 绿勾,detail "N 字节"
   - ③ 解析 PAC 预填路由 → 绿勾,detail "预填 N 条规则"
   - ④ 切换上游 server → 绿勾,detail "上游 IP:port · 本机 SOCKS5 :NNNN · 系统代理 已切换"
   - ⑤ 启动心跳与系统代理 → 绿勾,detail "心跳每 10 秒一次 · 流量统计已启用"
5. 5 步全绿后自动切到 ConnectedView,显示:
   - 顶部"已连接到 <server name>" + 右上"断开连接"按钮
   - 主信息卡:名称 / IP / 心跳胶囊(绿色"健康") / 已连接时长(实时 ticking)/ SOCKS / API / VPN
   - 流量曲线卡:上行(绿)+ 下行(蓝)双线 + 实时速率 + 累计字节
   - 路由命中卡:host / 方向 / 来源 / 命中数 / 最近使用
6. Sidebar 「已连接」标签出现绿色状态点

### 2.5 真实流量验收(同时验证 M-γ 的核心闭环)

打开任意浏览器,**不需要手动配代理**(连接时已自动切系统代理),正常访问:

| 站点 | 期望方向 | 期望来源 | 在 ConnectedView 路由命中表的表现 |
|---|---|---|---|
| https://www.baidu.com | direct | probe(本地 TCP 探测可通) | 第一次显示 direct/TCP 探测 |
| https://www.google.com | proxy | pattern(PAC 命中) | 显示 proxy/通配符 |
| https://github.com | proxy | pattern | 显示 proxy/通配符 |
| https://example.com | direct(海外但可直连) | probe | 显示 direct/TCP 探测 |

**同时观察**:
- 流量曲线立即出现尖峰
- 上行/下行实时速率刷新
- 累计字节单调增长
- 路由命中表行数增长

**如果不通过浏览器,而想验证后端**:
```bash

curl -fsS http://127.0.0.1:<client_api_port>/api/connection

# <client_api_port> 在 client 设置页可见(或 client sidecar 启动日志 "control API listening on 127.0.0.1:NNNN")

# 走 SOCKS5 测试(替换 NNNN 为 client SOCKS5 端口)
curl -sS --socks5-hostname 127.0.0.1:NNNN https://www.google.com -o /dev/null -w '%{http_code}\n'
```

### 2.6 「断开」验收

1. 在「已连接」页点右上"断开连接"
2. 状态切回 idle,卡片消失,提示"尚未连接"
3. ConnectedView 显示"去发现页"按钮
4. Sidebar 状态点消失
5. 此时浏览器访问 google.com 应该:**断了**(因为系统代理已恢复但 client 不再有上游)
6. 重新连接后自动恢复

### 2.7 「设置」页验收

进入 Sidebar 「设置」:

1. **运行时**:看到 SOCKS5 + Control API 端口
2. **手动连接 server**:输入 host/port 等可点「尝试连接」(用于 mDNS 不通的兜底,只能连之前发现过的)
3. **缓存维护**:显示当前缓存条目数 + 命中/未命中,可一键清空
4. **自检详情**:control_api / local_proxy 两条都绿
5. **关于**:显示版本

### 2.8 失败与降级路径验收

| 场景 | 操作 | 期望 |
|---|---|---|
| 连接中 server 突然挂 | 连接成功后,在终端 1 Ctrl+C 杀掉 server | 心跳胶囊 1 分钟内变黄/红;曲线归零;UI 显示"与 server 失联"警告 |
| 重连同一个 server | server 杀掉再重启 | mDNS 重新广播,卡片重新变绿;手动点连接重新走 5 步 |
| 连接到不存在的 server | 在设置页输入错误 host:port | toast 报"NOT_FOUND",状态保持 idle,无脏副作用 |
| connect 第 1 步失败(server 关机) | server 关机后立即点连接 | stepper 第 1 步红叉,显示具体错误,系统代理保持原状 |
| 二次连接同一 server | 已 connected 状态再点连接 | 后端返回幂等成功,状态不变 |
| 同时点连接两次 | 快速双击连接按钮 | 第二次返回 BUSY,UI 不会进入混乱状态 |

## 3. API 速查(给开发/调试用)

| 端点 | 方法 | 用途 |
|---|---|---|
| `/healthz` | GET | sidecar 探活 |
| `/api/servers` | GET | 当前发现的 server 列表(mdns + history) |
| `/api/connection` | GET | 当前连接快照 |
| `/api/connect/{server_id}` | POST | 连接(server_id = `name@host:port`) |
| `/api/disconnect` | POST | 断开 |
| `/api/cache` | GET | 路由缓存表(可加 `?direction=` `?source=` `?limit=`) |
| `/api/cache` | DELETE | 清空路由缓存 |
| `/api/traffic` | GET | 流量快照(总累计 + 当前秒) |
| `/api/events` | GET (SSE) | 实时事件流 |

**SSE 事件类型清单**:
- `ready` —— sidecar 启动完成
- `server_discovered` / `server_lost` —— mDNS 出现 / 消失
- `connection_state_changed` —— state ∈ {idle, connecting, connected, disconnecting, failed}
- `connect_progress` —— 5 步进度 ({step, total, key, label, status, detail, server_id})
- `connect_done` —— 与 connection_snapshot 同结构
- `heartbeat_changed` —— tone ∈ {green, yellow, red}
- `traffic_tick` —— 1Hz {ts, uplink_bytes, downlink_bytes, total_uplink, total_downlink}
- `route_decision` —— 每次决策 {host, port, direction, source, hit_count}

## 4. 故障排查

### Q1. 「发现」页一直空着,看不到任何 server

| 原因 | 解决 |
|---|---|
| macOS 「本地网络访问」未授权 | 设置 → 隐私与安全性 → 本地网络 → 勾上 client-app |
| zeroconf 模块未装 | `pip install zeroconf`,重启 client |
| 与 server 不在同网段 | mDNS 不跨网段;改用「设置」页手动连接 |
| 公司 WLAN 禁用 multicast | 同上;改用手动连接,或要 IT 解禁 |
| server 没起 mDNS | 检查 server 启动日志有没有 `mDNS advertised`;CONDUIT_NO_MDNS 环境变量是否被设了 |

### Q2. 连接 5 步卡在第 1 步(可达性检查)

server 端口被防火墙挡。直接 telnet 验证:

```bash
nc -zv <server_host> <server_socks_port>   # 应当 succeeded
nc -zv <server_host> <server_http_port>    # 应当 succeeded
```

### Q3. 连接成功但浏览器打不开网站

按顺序排查:

1. 是否系统代理切了?`networksetup -getsocksfirewallproxy Wi-Fi` 应该显示 `Yes`,`127.0.0.1:NNNN`
   - 如果是 `No`:client 启动时被加了 `CONDUIT_NO_SYSTEM_PROXY=1` 或 `--no-system-proxy`,需自己在系统设置里手动配 SOCKS5
2. SOCKS5 端口对吗?设置页可见
3. 直接走 curl 验:`curl -sS --socks5-hostname 127.0.0.1:NNNN https://www.google.com -o /dev/null -w '%{http_code}\n'`
   - 200 → 后端 OK,问题在浏览器/系统代理
   - 502/timeout → server 上游问题,看 server 日志

### Q4. 流量曲线一直是 0

只有真的过 client 的字节会被统计。如果浏览器请求都被 macOS 之前的代理或浏览器自身代理截走了,client 看不见。验法:用上一节 Q3 的 curl 命令直接走 SOCKS5,然后看曲线。

### Q5. 连接成功后断开,系统代理没自动还原

正常情况会自动 disable。如果没还原(异常崩溃),手动:

```bash
networksetup -setsocksfirewallproxystate Wi-Fi off
# 或在 macOS 设置 → 网络 → Wi-Fi → 详细信息 → 代理 → 关 SOCKS
```

下次启动 client 时 sidecar 也会探测并自动清理"指向自己的"残留代理(`cleanup_if_pointing_to_us`)。

### Q6. UI 进入了诡异状态,想从头开始

```bash
# 杀干净所有 sidecar
pkill -f proxy_server.py
pkill -f client_main.py
# 清掉 known-servers 历史
rm ~/Library/Application\ Support/Conduit/known-servers.json
# 重启
pnpm dev:server &
pnpm dev:client &
```
